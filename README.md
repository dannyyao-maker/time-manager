# Time Manager

**把行事曆和每日待辦整合成一個網站，取代 TimeTree ＋ Notion 的雙工具流程。**
A personal calendar + daily to-do web app where events and tasks are the same data, with a read-only "free/busy" view for my partner.

正式網站：https://time-manager-wine.vercel.app （私人網站，需要受邀的 Google 帳號才看得到內容）

---

## 為什麼做這個

我原本用 TimeTree 排行程、用 Notion 列每日待辦，遇到三個問題：

1. **同一個行程要輸入兩次**：自己的行事曆一次，再複製到和女友的共同行事曆，她才看得到我什麼時候有空。
2. **Notion 每週要重建表格**，還要對照行事曆手動抄固定行程（上課、社團例會）。
3. **兩邊不會同步**：在一邊勾完成，另一邊不會更新。

## 核心設計：只有一種「項目」

行程和待辦是**同一種資料**，只是欄位填得不一樣：有時間的出現在行事曆時間軸上，沒時間的就是當天待辦。
月曆、週曆、每日清單只是**同一份資料的不同看法**，任何一邊勾選或修改，其他地方同步更新。每筆資料只存一份，分享給女友也不需要複製。

## 功能

| 功能 | 說明 |
| --- | --- |
| 月曆／週曆／日曆 | 一週從週日開始；跨天項目畫成長條；時間重疊的項目並排；拖拉就能改時間 |
| 每日清單 | 像 Notion 表但不限筆數；勾選完成、進度條、快速新增待辦 |
| 重複行程 | 每天／每週／每月＋結束日期；可以「只改這一次」（停課、調課）或「改整串」；每一次分開勾完成 |
| 類別 | 10 色標籤；刪除前顯示會一起刪掉幾筆 |
| 三個行事曆 | 我的／共用／她的：自己的行程在對方眼中只顯示名字（點／宛），點進去才看細節；「一起」的約會兩人都能改；權限由資料庫擋住，不是只藏按鈕 |
| 可約 | 共用行事曆標出「可約」的日子：12–22 點兩人都沒安排的時間加起來滿 5 小時；上方列出接下來一週最適合約的日子 |
| 備份 | 一鍵下載 JSON（完整備份）＋ CSV（Excel 可開） |
| 手機 | 可加到主畫面當 App（PWA）；下方分頁列；點日期先看當天清單；新增頁用小月曆和時間滾輪 |

## 技術選擇

| 用途 | 技術 | 為什麼 |
| --- | --- | --- |
| 網站畫面 | React 19 + Vite + TypeScript | 最主流；TypeScript 在寫錯欄位時就提醒 |
| 行事曆元件 | FullCalendar 6 | 成熟的月／週曆元件，省下自己處理日期格線 |
| 資料庫＋登入 | Supabase（Postgres + Auth） | 關聯式資料適合「項目／類別／單次覆寫」；內建 Google 登入；RLS 在資料庫層控管權限 |
| 部署 | Vercel | 推上 GitHub 就自動更新網站 |
| 自動測試 | Vitest | 日期和重複規則最容易出錯，用 63 項測試把關 |

全部使用免費方案；兩人的用量遠低於各服務的免費額度。

## 架構

```
瀏覽器（電腦／手機）
   │
   ▼
Vercel：網站畫面（公開，但裡面沒有任何資料）
   │  讀寫（每次都帶著登入身分）
   ▼
Supabase
 ├─ Auth：Google 登入
 ├─ Postgres：members／categories／items／occurrence_overrides
 └─ RLS：資料庫自己檢查「你是誰、能做什麼」
```

### 資料結構

| 資料表 | 內容 |
| --- | --- |
| `members` | 誰能進來、角色（owner／editor 可編輯、viewer 只能看）；只在後台設定 |
| `categories` | 類別名稱、顏色 |
| `items` | 項目；屬於個人或共用行事曆；重複項目只存一筆規則（每天／每週／每月＋結束日期） |
| `occurrence_overrides` | 重複項目的「某一次」：停課、改時間、這一次勾完成 |

重複項目不會被拆成幾十筆存起來，而是畫面依規則即時算出每一次，再套用單次覆寫（`src/lib/recurrence.ts`）。

## 隱私與安全（repo 是公開的）

- **資料只在資料庫，程式碼裡沒有任何行程或個人資料。**
- 權限由 Postgres 的 **RLS（Row Level Security）** 負責：
  - 不在成員名單上的人：就算登入，也讀到 0 筆。
  - viewer：可以讀，但新增／修改／刪除一律被資料庫拒絕。
  - owner：只能修改自己的資料。
- `supabase/tests/rls_test.sql` 模擬沒登入、陌生人、viewer、editor、owner 五種身分，21 項權限測試（例如「女友不能改我的個人行程，但能改共用項目」）。
- 網站裡的 Supabase「公開金鑰」設計上可以公開：它只能以訪客身分發出請求，每個請求都還要過 RLS。能繞過 RLS 的 secret key 從不出現在網站或 repo。
- 每次 commit 前自動執行 `scripts/check-secrets.mjs`，擋下 Gmail 地址、金鑰和環境變數檔。

## 在自己電腦上執行

需要 Node.js 20 以上，以及自己的 Supabase 專案。

```bash
npm install
cp .env.example .env.local   # 填入 Supabase 網址和公開金鑰
npm run dev                  # 打開 http://localhost:5173
npm test                     # 執行自動測試
```

資料庫：依序在 Supabase SQL Editor 執行 `supabase/migrations/` 裡的 `0001`～`0004`，再用 `supabase/setup/add_member.example.sql` 把自己加進成員名單。

## 開發過程

這個專案用 [Claude Code](https://claude.com/claude-code) 協作完成。我負責需求、設計決策和測試，過程都留有紀錄：

- [`提案.md`](提案.md)：要解決的問題、功能盤點（TimeTree／Notion 各自的功能逐項比對）
- [`階段0規劃.md`](階段0規劃.md)：技術比較、資料結構、權限設計、開發階段與完成標準

開發分成 7 個階段：規劃 → 登入與資料庫 → 新增／編輯 → 月曆週曆 → 每日清單 → 重複行程 → 女友檢視與備份，每個階段都有明確的完成標準，由我實際測試通過後才進下一階段。
